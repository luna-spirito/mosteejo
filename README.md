# rp-bot

ИИ-агент для ведения групповой ролевой игры в Telegram. «Мини-deepseek-harness
в коробке»: агентный цикл с инструментами (терминал, файлы, Telegram),
автоматической компакцией контекста и работой на OpenAI-совместимом API
(Z.ai). Ориентир по устройству — [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness):
append-only журнал сессии, «поверхность» (surface) сообщений, выводимая из
журнала, и компакция, которая ничего не переписывает, а добавляет операции.

## Как это устроено

```
poller (getUpdates) ──> фильтр ingress ──> inbox (очередь) ──> agent loop ──> Z.ai
                            │                  │                  │
                     чужие пользователи   priority-пинг      инструменты:
                     и чужие реакции      будит мгновенно    bash / read_file /
                     дропаются ДО модели                     write_file / edit_file /
                                                             send_message / edit_message
```

* **Строгая фильтрация на входе.** Обновления от пользователей вне
  `telegram.allowed_users` отбрасываются в поллере и при выдаче агенту — их
  содержимое вообще не попадает в контекст модели. Это граница защиты от
  prompt-injection.
* **Пробуждение.** Мгновенно: личка, сообщение в подписном топике
  (`chat_id, thread_id`), `@упоминание` бота, ответ на сообщение бота,
  реакция в личке/подписном чате, команда `/...`. Остальное (разрешённые
  пользователи в прочих топиках/чатах, прочие реакции) копится в очереди и
  отдаётся при плановом пробуждении — раз в `idle_wake_secs` (по умолчанию
  10 минут). При каждом пробуждении агент получает **все** накопленные
  обновления одним сообщением; заголовок вида `[Telegram: 3 new update(s)
  from RP, News; …]` перечисляет чаты-источники. Пустой тик превращается в
  heartbeat («можешь подвигать сцены сам»), отключается
  `agent.heartbeat = false`.
* **Единый «мозг»**: одна сессия на всё (все каналы и лички), контекст
  размечен заголовками вида `--- [время] Автор в <канал>, message #N`.
  Адресация — по именам каналов, без числовых id.
* **Каналы и логи.** Каждый DM, группа и **каждый форумный тред — отдельный
  канал** со своим именем. Имена бот узнаёт пассивно из апдейтов
  (`forum_topic_created` у service-сообщения или в `reply_to_message`
  обычного сообщения треда; для лички — имя человека) и замораживает при
  первой регистрации: переименование канала ничего не меняет, заодно
  оставаясь стабильным имя файла лога. Список каналов вшивается в голову
  контекста сразу после системного промпта (секции `DM channels` /
  `Group channels`) при старте и пересканируется при каждой компакции;
  резолв имени в `send_message` всегда идёт по живому реестру, так что
  канал, узнанный посреди сессии, адресуем немедленно. Параллельно реестру
  ведётся человеческая история: `workspace/chat/<имя>.log` на канал,
  append-only строки вида `[ts] #87 Luna: текст`, `EDIT #90 …`,
  `REACT ❤ #191 …` и `SENT/EDIT` для собственных отправок бота (включая
  ответы на `/model`) — модель читает её обычными `read_file`/grep'ом.
  Инструменты `list_chats`/`read_chat` больше не нужны и удалены; старый
  `state/chats.json` при первом старте дампится в `<имя>.legacy.log`
  (треды там не различить) и переименовывается в `chats.json.migrated`.
* **Реакции.** `getUpdates` подписан и на `message_reaction`: агент видит
  «Alice (@alice) reacted to message #7 in IC: 🔥 (was: (none))» — и снятие
  реакции (пустой `new_reaction`) тоже, строкой `UNREACT` в логе. Анонимные
  реакции админов сопоставляются с allowlist по `actor_chat`; реакции чужих
  людей отбрасываются на входе, как и чужие сообщения. Telegram не указывает
  в реакции тред, поэтому реакция пишется в лог группы, а не топика.
* **Сессия** — по файлу на поколение: `state/sessions/<ts>.jsonl` с
  append-only операциями `append`, `state/current` указывает на активный.
  Системный промпт в журнале не хранится вовсе — он вставляется в голову
  контекста из конфига при каждом запросе, так что рестарт сервиса с новым
  промптом меняет его мгновенно и для всей истории. Вторым сообщением в
  голове идёт замороженный список каналов: он выводится из реестра при
  старте и пересканируется при компакции, а между ними не меняется ни на
  байт (стабильный префикс — тёплый префиксный кэш). Поверхность при этом
  всё равно append-only: каждый запрос — тупой `.push` без пересборки.
  Компакция ротирует
  сессию: новый файл начинается с чекпоинта и хвоста, старый остаётся
  архивом — файлы ограничены по размеру. Старый однофайловый формат
  (`session.jsonl`) мигрирует автоматически при первом старте (файл
  переименовывается в `session.jsonl.migrated`). Падение посреди turn'а
  лечится при загрузке: неотвеченным tool-call'ам проставляются
  синтетические ошибки.
* **Инструменты** не роняют цикл: любая ошибка превращается в текст
  `Error: ...` для модели. `bash` — `bash -c` в `workspace_dir`, таймаут
  120 с (макс. 600 с), хвост stdout/stderr 64 KiB. `read_file` — окно 2000
  строк с нумерацией и offset-постраничностью. `edit_file` — литеральная
  замена с проверкой уникальности.
* **Компакция.** Триггер — **реальные** токены провайдера: `usage.prompt_tokens`
  последнего запроса плюс оценка хвоста, дописанного уже после ответа (до
  первого ответа — чистая оценка, 4 символа/токен, изображение ≈ 1500). Это
  делает порог независимым от качества эвристики: для русского текста оценка
  занижает токены примерно вдвое, провайдерский счётчик — истина. Порог —
  `compaction_threshold_tokens` (сравнивай с настоящим `prompt=` из лога, окно
  модели должно быть заметно больше), хвост сохраняется дословно
  (`compaction_retain_tokens`), границы срезов не рвут пары
  tool-call/tool-result. Компакция выполняется **сразу по завершении хода
  агента**, в паузе, когда запросов нет: реальные `prompt_tokens` уже
  известны, а следующее сообщение пользователя не платит за суммаризацию
  своим откликом. Единственная защита внутри хода — переполнение от
  провайдера (форс-компакция и один повтор); после компакции якорь
  сбрасывается до первого нового ответа. Суммаризация — отдельный
  **агентный** проход:
  все инструменты доступны, включая Telegram (инструкция просит писать в чат
  только при необходимости; лимита шагов нет). Запрос суммаризатора повторяет surface
  дословно + инструкция последним сообщением — префиксный кэш провайдера
  остаётся тёплым. Итог оборачивается в `<compacted-summary>` с preamble.
* **Кэширование.** Форма запроса стабильна: system в голове, фиксированный
  массив tools, append-only сообщения. Попадания видны в логе: строка
  `llm usage prompt=… cached=…` на каждом запросе. Если провайдер ответил
  переполнением контекста — компакция форсируется и запрос повторяется один
  раз.
* **Медиа.** Фото скачиваются в `workspace/downloads/` и уходят в модель как
  image-блоки (data URL), документы — файлами на диске (агент читает их
  инструментами).
* **Markdown в исходящих.** Модель пишет обычный Markdown, бот рендерит его в
  HTML-диалект Telegram (`parse_mode: HTML`): `**жирный**`, `*курсив*`,
  `~~зачёркнутый~~`, `` `код` ``, fenced-блоки кода, `>` цитаты, `#`-заголовки,
  списки, `[текст](url)`. HTML-вывод всегда сбалансирован — Telegram не может
  отклонить сообщение из-за разметки; таблицы и картинки в строке деградируют
  в текст. Длинные тексты режутся по границам абзацев, каждая часть рендерится
  независимо.
* **Модель и reasoning effort.** Управление из чата: `/model` — показать
  текущую, `/model glm-5.3` — сменить модель, `/model glm-5.3-flash:high` —
  модель + effort, `/model :low` — только effort (GLM-5.3* понимает
  `low|high|max`). Выбор переживает рестарт (`state/model.json`), команды
  никогда не попадают в контекст модели. Компакция всегда суммаризирует с
  `low`.
* **Preserved thinking.** Агент с инструментами по гайду Z.ai обязан
  возвращать модели её же рассуждения: `reasoning_content` каждого хода
  хранится в журнале сессии и воспроизводится дословно и в исходном порядке,
  а в запросах отправляется `clear_thinking: false` (на стандартном эндпоинте
  сохранение выключено по умолчанию). Это улучшает качество цепочек
  tool-call → tool-result и поднимает долю кэш-попаданий по префиксу.
  Граница компакции — единственное место, где старые рассуждения исчезают:
  свёрнутый хвост попадает в чекпоинт-саммари, а сохраняемый хвост несёт
  свои `reasoning_content` дальше как есть. Отключается:
  `preserve_thinking = false` в `[llm]`.

## Запуск

```bash
nix develop                # или любой rust 1.85+
cp rp.toml.example rp.toml # прописать token/ключи/пользователей/топики
export TELEGRAM_BOT_TOKEN=...
export ZAI_API_KEY=...
cargo run -- rp.toml       # или: nix run
```

Логи: `RUST_LOG=info` (по умолчанию), `RUST_LOG=debug` подробнее.

Сборка пакетом: `nix build .#rp-bot`.

## Развёртывание

Флейк собирается через crane: зависимости строятся отдельной деривацией
(`buildDepsOnly`), поэтому апдейт исходников пересобирает только сам `rp-bot`,
а артефакты зависимостей остаются в store — частые обновления дешёвые даже на
медленной машине. Пакет доступен для всех систем флейка, включая
`aarch64-linux`: на сервере его достаточно собрать нативно
(`packages.aarch64-linux.default` из вашего конфига-флейка) — кросс-компиляция
и binfmt не нужны. В деривацию входят только исходники cargo
(`cleanCargoSource`); конфиг (`rp.toml`), `state/` и `workspace/` живут рядом с
процессом и настраиваются юнитом. Пример ссылки из NixOS-конфига:

```nix
# flake input:
#   rp-bot.url = "github:<you>/rp-bot";  # или path:/srv/rp
environment.systemPackages = [
  rp-bot.packages.${pkgs.system}.default  # на aarch64-сервере соберётся нативно
];
```

Чеки флейка (`nix flake check`) гоняют clippy (`-Dwarnings`) и тесты на тех же
кэшированных зависимостях.

Есть готовый NixOS-модуль (`rp-bot.nixosModules.default`, [module.nix](module.nix)):
конфигурация описывается опциями `services.rp-bot.*` и рендерится в `rp.toml`
без секретов (он попадает в world-readable store — см.
`services.rp-bot.configFile`), а секреты передаются через systemd-механизм
credential'ов:

```nix
services.rp-bot = {
  enable = true;
  package = rp-bot.packages.${pkgs.system}.default;
  credentials = {
    telegram_bot_token = config.age.secrets."tg-token".path;   # или sops/файл
    zai_api_key = "/var/lib/secrets/zai.key";                  # или systemd-creds encrypt
  };
  telegram.allowedUsers = [{ id = 740313423; name = "Luna"; }];
  telegram.subscribedTopics = [{ chatId = -1001234; threadId = 42; }];
  agent.systemPrompt = ''
    Ты — трактирщик в фэнтезийной таверне. Веди сцену, не пиши за игроков.
  '';
  llm.reasoningEffort = "low";
};
```

Бот читает секреты из `$CREDENTIALS_DIRECTORY` (`LoadCredential`), env-переменные
`TELEGRAM_BOT_TOKEN`/`ZAI_API_KEY` — запасной путь для локальной разработки.
Юнит жёстко sandbox'ится (DynamicUser, ProtectSystem=strict и т.д.); bash-инструмент
агента работает внутри той же песочницы — писать он может только в workspace.

Куда смотреть при запуске:
* `state/sessions/*.jsonl` + `state/current` — поколения сессии (активный
  файл — по указателю, остальные — архивы прошлых компакций);
* `state/channels.json` — реестр каналов (имя ↔ chat/thread, файл лога);
* `workspace/chat/*.log` — история по каналам (сообщения, правки, реакции,
  собственные отправки бота);
* `state/tg_offset` — позиция long-poll (после рестарта старые обновления не
  переигрываются);
* `workspace/` — рабочий стол агента (его заметки, `downloads/`, `notes/`).

## Что осознанно не сделано (кандидаты на следующую итерацию)

* NixOS-модуль для microvm (systemd-сервис, опции, stateDir) — уже написан,
  см. «Развёртывание».
* Потеря обновлений при падении между persist offset'а и обработкой
  (окно мало, но не ноль); надёжный вариант — подтверждать offset после
  обработки агентом.
* Исходящие файлы/картинки (`send_document`), streaming-ответы.
* Отдельные схемы инструментов для суммаризатора кэшируются хуже
  (tools-массив меняется на время компакции) — приемлемо, компакция редка.
